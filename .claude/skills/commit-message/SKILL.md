# Git コミットメッセージ作成

現在の変更内容を確認し、以下のルールに従ってコミットメッセージを作成する。

## フォーマット

1行目: `プレフィックス: 概要`
2行目: 空行
3行目以降: 修正した詳細内容

概要・詳細内容ともに極力日本語を使用する。概要で十分な説明ができる場合には2行目以降の詳細内容は省略可能とする。

## プレフィックス一覧

| プレフィックス | 分類 | 内容 / 主な使用場面 |
| :--- | :--- | :--- |
| `feat:` | 新機能 | 新しい機能、画面、APIの追加 |
| `fix:` | バグ修正 | 不具合や挙動・表示のバグ修正 |
| `refactor:` | 改善 | 外部挙動を変えずに構造整理・コードを綺麗にする |
| `style:` | 書式 | コードの意味に影響しないフォーマット・空白・記号などの調整 |
| `docs:` | ドキュメント | READMEやインラインコメント、各種仕様書の追加・修正 |
| `test:` | テスト | テストコードの追加・修正・テスト設定の変更 |
| `chore:` | 雑務 | 依存ライブラリの更新、環境設定、その他雑多な作業 |
| `perf:` | パフォーマンス | 処理速度の向上、メモリ消費の削減など |
| `build:` | ビルド | ビルドツールや外部依存関係の変更（npm/pipパッケージ追加等） |
| `ci:` | CI/CD | GitHub Actions、GitLab CIなどCI/CD設定の変更 |
| `revert:` | 打ち消し | 過去のコミットを取り消す（打ち消しコミット） |

## 手順

1. `git status` と `git diff`（ステージ済みの変更があれば `git diff --staged` も）で変更内容を確認する。対象リポジトリが複数ある場合（例: 本プロジェクトの `frontend` / `api` / `batch` のようにサブディレクトリごとに独立したGitリポジトリを持つ構成）は、変更があったリポジトリごとに個別のコミットメッセージを作成する。
2. 変更内容の性質から、上記の表に沿って最も適切なプレフィックスを1つ選ぶ。判断基準は次の通り。
   - 実際の挙動や見た目が変わる修正・追加 → `fix:` / `feat:`
   - 外部から見た挙動を変えない構造整理 → `refactor:`
   - 見た目に影響しない書式のみの変更（インデント・空白・記号など） → `style:`
   - 上記以外は表の分類に従う
3. 概要（1行目）は変更内容を一言で表す短い日本語にする。
4. 詳細（3行目以降）には、何をどう修正したかを箇条書きまたは短い文章で日本語で記載する。
5. 完成したメッセージをユーザーに提示する。コミットの実行まで依頼されている場合は、このメッセージを使って `git commit` を行う。
